## vision-plugin 图片识别故障修复

**现象**：发送图片报「模型不支持图片输入」；设置页「图片识别」开关 OFF 且无法持久化。

**根因与修复（全部局限在 vision-plugin 内，未改动 dsh 源码）**：

1. `src/index.ts`
   - 新增 `patchInfo` / `wrapPrototypeMethod` 帮助函数，统一包装原方法后注入 `image` 能力。
   - `installImageGuardBypass` 同时 patch `resolveModelInfo` **和** 运行时原型上的私有方法 `resolveModelInfoFor`（`prepareCall`/`resolveCallConfig` 内部调用的是后者），确保 api-proxy 的图像准入路径也看到 image 支持。
   - `attachments === undefined` 时从「透传原始请求」改为抛出明确错误，避免把 raw image 交给 text-only 模型复现原报错。
   - `apply` 注入改为 `['settings','llm','attachments']`，保证转写运行时 attachments 服务已就绪。

2. `src/client/index.ts`
   - `onToggle` 增加 `if (state.saving || !state.writable) return` 守卫。
   - `saveSection` / `onToggle` 的 catch 增加 `console.error` 日志。
   - tab inject 新增 `failed`、`writable` 两个 `HostObservable<boolean>` hook。

3. `src/client/VisionPluginsTab.tsx`
   - 组件消费 `useFailed` / `useWritable`，展示 `saveFailed` / `readOnly` 文案。
   - 按钮禁用条件由 `saving` 改为 `saving || !writable`。

4. `package.json`：修正 `dsh.client.inject` 数组缩进（内容未变）。

**验证**：每次修改后运行 `node build.mjs` 均构建成功（`✓ built lib/index.js`、`✓ built lib/client.js`）。

**结论**：改动需重启 dsh 应用后生效。

## 关键坑：workspace 改动不生效（"没变啊"）

**根因**：DSH 通过 `file:D:/code_files/dsh_workspace/@dsh/vision-plugin` 依赖安装插件，且 profile 的 `pnpm-workspace.yaml` 设 `nodeLinker: hoisted`（复制而非软链接）。因此 DSH 实际加载的是：
- `~/.dsh/profiles/default/node_modules/@dsh/vision-plugin/lib/`
- `~/.dsh/profiles/web/node_modules/@dsh/vision-plugin/lib/`（web profile 才是 GUI 实际使用的，bundles 含 `dsh-web-app`）

在 workspace 里 `node build.mjs` 只更新 workspace 的 `lib/`，不会同步到 profile，导致重启后 UI 无变化。

**解决**：
1. 手动把 workspace 的 `lib/index.js`、`client.js`、`client.js.map` 复制到上述两个 profile 副本。
2. 新增 `sync.mjs` 脚本 + package.json 的 `npm run sync`，自动扫描 `~/.dsh/profiles/*/node_modules/@dsh/vision-plugin/lib/` 并同步三个产物。

**后续工作流**：改代码 → `node build.mjs` → `node sync.mjs` → 重启 DSH。

## 修复 namespace unavailable + 插件 tab 空白

**现象**：重启 DSH 后，「识图模型配置」页面显示"无法读取识图配置：设置命名空间未注册"；「插件 → 图片识别功能」tab 空白。

**根因**：`src/index.ts` 此前改为双 inject 结构：
```ts
let scope
ctx.inject(['settings'], (settingsCtx) => { scope = settingsCtx.settings.register(...) })
ctx.inject(['settings', 'llm'], (both) => { if (scope === undefined) return; ... })
```
scope 跨 inject 保存，namespace 注册时序/生命周期异常，导致客户端 `settingsScope.bind` 读取到 `unavailable`，tab 因无可用状态而空白。

**修复**：回到已被旧版验证可行的单 inject 结构：
```ts
ctx.inject(['settings', 'llm'], (both) => {
  const scope = both.settings.register(...)
  installImageGuardBypass(both, scope, both.llm)
  installImageTranscription(both, scope, both.llm)
})
```
同时保持 `exposeSettingsNamespace` 移除（模型页面不显示 Vision Plugin 卡片）。

**验证**：`node build.mjs && node sync.mjs` 成功；两个 profile 的 `lib/index.js` 均为单 inject 且无 `exposeSettingsNamespace`。

**结论**：重启 DSH 后，「图片识别功能」tab 应恢复开关卡片，「识图模型配置」页面应正常加载，「模型」页面不再显示 Vision Plugin 卡片。

## 最终修复：完整同步 workspace + 健壮化 apply

**现象**：用户报告"还是不行"，截图仍显示「识图模型配置」unavailable 且「插件 → 图片识别功能」tab 空白；同时检查到 DSH 进程仍在运行（PID 28212，占用 127.0.0.1:3080），说明用户此前未真正完全退出 DSH。

**额外根因**：
1. `sync.mjs` 只同步 `lib/` 产物，profile 里的 `src/` 仍是旧版本；若 DSH/HMR 路径读取 `src/`，会拿到旧代码。
2. 单 inject 结构下，`llm` patch 阶段若抛异常会带崩整个 fiber，连带撤销已注册的 namespace。

**修复**：
1. `src/index.ts`：改为双 inject，namespace 注册独立在 `['settings']` inject 中；`['settings','llm','attachments']` inject 中安装 image pipeline，并包 `try/catch` 防止 patch 失败撤销 namespace。
2. `sync.mjs`：递归同步整个 workspace（除 `node_modules`、`.git`、`lib` 外）到 profile 副本，再把最新 `lib/` 产物显式覆盖进去，确保 `src/`、`package.json`、`cordis.patch.yml` 等也一致。
3. `src/client/index.ts`：补全 tab inject face 缺失的 `failed` 与 `writable` hooks；`onToggle` 增加 `saving || !writable` 守卫与 `console.error`；`saveSection` catch 也增加 `console.error`。
4. 构建并同步到 default 与 web profile。

**关键发现——tab 空白的直接原因**：
`VisionPluginsTab.tsx` 组件已消费 `useFailed` / `useWritable`，但 `src/client/index.ts` 的 `tabInjected()` 只提供了 `enabled` / `saving` 两个 hooks，导致 `useFailed` / `useWritable` 为 undefined，组件渲染时抛出异常，tab 区域空白。

**验证**：
- `node build.mjs && node sync.mjs` 成功。
- profile `src/index.ts`、`src/client/index.ts`、`lib/index.js`、`lib/client.js`、`package.json` 均与 workspace 一致。
- `netstat` 确认旧 DSH 进程仍在占用 3080，需用户彻底退出后重启。

**结论**：请用户在任务管理器中结束所有 DSH/node 相关进程（或点击系统托盘退出），再启动 DSH；重启后「识图模型配置」与「图片识别功能」tab 应恢复正常。

## dsh-skill-hub 与 dsh slot 契约不兼容

**现象**：DSH 启动时 HARNESS 报错 `Failed to load plugins: dsh-skill-hub: keyed slot "settings.plugin.item" requires options.key`。

**根因**：当前 dsh 版本的 `settings.plugin.item` 是 `keyed` slot（按 namespace key 分发卡片），但 `dsh-skill-hub` 的 `lib/client.js` 仍按旧 `list` 契约注册（传 `id: NS` 而非 `key: NS`），导致注册失败。

**修复**：直接把 profile 副本里的旧 `id: NS` 改成 `key: NS`：
1. `C:/Users/25366/.dsh/profiles/web/node_modules/dsh-skill-hub/src/client/index.tsx`
2. `C:/Users/25366/.dsh/profiles/web/node_modules/dsh-skill-hub/lib/client.js`

注意：这是**修改了 profile 里的第三方插件副本**，不是改 dsh 源码；如果后续 `dsh plugin install` 重新装 dsh-skill-hub 会覆盖回来。长期方案是等 dsh-skill-hub 发布兼容新契约的版本，或在 dsh 侧降级兼容。

**验证**：default profile 未安装 dsh-skill-hub，只有 web profile 受影响。修复后 DSH 应能正常加载该插件。
